## Context

The editor currently keeps visual decisions in multiple places:

- CSS custom properties at the top of `EditorPage.module.css`.
- TypeScript constants for DBML diagram relation colors and highlights.
- Monaco theme definitions inside `editor-theme.ts`.

That worked while the editor had one mostly fixed palette, but the current theme work already requires keeping CSS, React Flow SVG rendering, and Monaco in sync. The project is still small enough to introduce a stricter source-of-truth model without a long-lived mixed styling system.

This change introduces Style Dictionary as a build-time design token compiler. Both light and dark themes are tokenized in the initial migration so the frontend does not carry two styling systems for themed values.

## Goals / Non-Goals

**Goals:**

- Introduce a frontend-local Style Dictionary pipeline.
- Store human-authored design tokens under `frontend/design-tokens/`.
- Model tokens in primitive, semantic, and component layers.
- Generate app-consumable CSS variables and TypeScript values under `frontend/src/shared/design-tokens/generated/`.
- Make the light and dark editor workspace, diagram, relation colors, sidebar chrome, and Monaco themes consume generated token outputs.
- Define the light theme as a light reinterpretation of the dark theme's semantic roles, not as a verbatim copy of the current light colors.
- Add verification that generated token outputs match the source JSON.
- Keep generated files clearly marked as generated and out of manual editing.

**Non-Goals:**

- Replacing CSS Modules with CSS-in-JS.
- Creating an app-wide runtime theme provider beyond the editor theme state already present.
- Adding user-customizable theme palettes.
- Reworking layout, spacing, or component structure beyond what is needed to consume generated token values.

## Decisions

### Keep token source outside `src`

Place human-authored token JSON under `frontend/design-tokens/`:

```text
frontend/
  design-tokens/
    primitive/
    semantic/
    component/
```

Rationale: these files are build input resources for Style Dictionary, not runtime React modules and not browser-served assets. Keeping them outside `src` separates authored token source from app code.

Alternative considered: `src/shared/design-tokens/source/`. That would make imports and FSD placement look tidy, but it blurs the distinction between generated runtime modules and build input resources.

### Put generated artifacts under `src/shared/design-tokens/generated`

Generate runtime artifacts under:

```text
frontend/src/shared/design-tokens/generated/
  tokens.css
  tokens.ts
  monaco-themes.ts
```

Rationale: generated CSS and TS are consumed by app code and are design-system infrastructure without business logic, which fits the `shared` layer. The `generated` segment makes ownership explicit.

Alternative considered: emit generated artifacts next to the token source. That keeps all token-related files together, but forces app code to import from a build-resource directory outside `src`.

### Use primitive, semantic, and component token layers

Use three token layers:

- Primitive tokens hold raw palette and scale values, such as Gruvbox Material colors.
- Semantic tokens assign product meaning, such as text, surface, source accent, destination accent, and relation line.
- Component tokens map semantic values into concrete UI surfaces, such as editor toolbar title, sidebar active control, diagram table title, relation edge gradient, and Monaco token colors.

Rationale: primitive tokens make palette updates possible, semantic tokens prevent components from depending on raw palette names, and component tokens give UI-specific names where a semantic token alone is too broad.

Alternative considered: only primitive and semantic layers. That is simpler, but it would push component-specific decisions back into CSS and TypeScript.

### Tokenize light and dark themes together

Both light and dark theme values are authored in `frontend/design-tokens/` and generated by Style Dictionary in this change. The light palette should be designed from the same semantic roles as the dark palette: text, title, source accent, destination accent, relation line, surface, panel, border, control, diagnostics, and Monaco syntax roles.

Rationale: leaving light values outside the token source would preserve the exact mixed-system problem this change is meant to remove. Tokenizing both themes keeps the styling contract strict from the first implementation and prevents future contributors from treating light as a legacy exception.

Alternative considered: tokenize dark first and migrate light later. That reduces immediate palette work, but it creates a confusing intermediate state where the app has two sources of truth for equivalent theme decisions.

### Reinterpret light from dark semantics

The light theme should not preserve the current VS Code Light 2026-inspired values verbatim. Instead, start from the dark theme's semantic intent and choose light-mode values that express the same relationships:

- title and source accents remain a yellow family;
- destination/reference accents remain a cyan family;
- default relation lines follow normal text color;
- surfaces, borders, muted text, and control states preserve the same hierarchy as dark mode with light-compatible contrast;
- Monaco syntax roles should stay semantically aligned with the workspace palette.

Rationale: this keeps both themes recognizably part of the same product design language while allowing light mode to improve instead of freezing the current palette.

Alternative considered: copy the current light colors into tokens. That would be mechanically cleaner but would encode a palette the user has already identified as not the desired end state.

### Generate both CSS variables and TypeScript tokens

Generate CSS variables for CSS module consumption and TypeScript exports for non-CSS consumers:

- CSS modules read generated custom properties such as `--editor-color-relation-source`.
- Diagram rendering code reads generated token references or CSS-variable-backed constants.
- Monaco theme definitions are generated or assembled from generated TS token values.

Rationale: CSS variables are the right consumption model for most UI styling, while Monaco and SVG rendering code need TypeScript-accessible values or stable CSS variable references.

Alternative considered: use only CSS variables. That would simplify output, but Monaco theme registration cannot reliably consume CSS variables as resolved color values.

### Keep CSS Modules for structure and state styling

CSS Modules continue to own layout, selectors, interaction states, and component structure. Theme design values move to generated variables.

Rationale: the current problem is duplicated design values, not CSS selector ownership. Style Dictionary addresses the value pipeline without forcing a CSS-in-JS migration.

Alternative considered: introduce CSS-in-JS now. That would add runtime styling machinery before the token source-of-truth problem is solved.

### Add token drift checks to frontend verification

Add frontend scripts for building and checking token outputs. Verification must fail when token JSON and generated artifacts drift.

Rationale: generated files become part of the app source consumed by Vite and tests, so CI needs to catch stale output.

Alternative considered: generate tokens only during `build`. That keeps local development lightweight but allows stale generated files to pass review until a production build runs.

## Risks / Trade-offs

- [Risk] Tokenizing both themes increases initial migration size. → Mitigation: keep the migration scoped to theme design values and avoid unrelated layout or component refactors.
- [Risk] The reinterpreted light palette may need visual tuning after implementation. → Mitigation: keep semantic/component token names stable so palette values can be adjusted without touching consuming CSS or TypeScript.
- [Risk] Generated TS and CSS can drift from JSON. → Mitigation: add a token check script and include it in frontend verification.
- [Risk] Style Dictionary output names may not match the existing CSS variable contract. → Mitigation: define a stable naming transform or custom format that emits the existing `--editor-*` variable names where possible.
- [Risk] Monaco theme generation may need custom formatting beyond built-in Style Dictionary formats. → Mitigation: generate a small typed token module first, then assemble Monaco theme objects from generated values if a full custom Monaco format is too heavy.
- [Risk] Hard-coded theme values can reappear during future edits. → Mitigation: add targeted tests or lint-like checks for raw palette literals in editor UI and rendering files after migration.

## Migration Plan

1. Add Style Dictionary and frontend token scripts.
2. Add light and dark primitive, semantic, and component token JSON.
3. Generate CSS and TypeScript token outputs.
4. Import generated CSS once in the frontend app or editor entry path.
5. Replace light and dark CSS custom property values with generated token variables.
6. Replace diagram relation and highlight color constants with generated token references.
7. Replace Monaco color definitions with generated token values.
8. Add verification for token generation drift and run the frontend quality checks.

Rollback is straightforward: remove the token build dependency and generated imports, then restore the previous CSS custom property and TypeScript color definitions from version control.

## Open Questions

- Should generated CSS preserve the current `--editor-color-*` variable names exactly, or should we introduce a new `--dbml-*` naming convention and migrate selectors at the same time?
- Should generated token artifacts be committed, or should they be generated during install/build only? The current recommendation is to commit them and enforce drift checks for simpler Vite/test consumption.
